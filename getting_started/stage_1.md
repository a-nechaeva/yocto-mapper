# Генерация SBOM и анализ уязвимостей

## Включение и генерация SBOM
Включим генерацию SBOM в конфигурации. Для этого добавим в `conf/local.conf` обеих сборок (a и b):
```bash
INHERIT += "create-spdx"
SPDX_PRETTY = "1"
```
`SPDX_PRETTY` делает JSON-файлы внутри архива отформатированными для удобства чтения.

И пересоберем отдельно каждый образ командой `bitbake core-image-minimal`.

После сборки артефакты SBOM будут находиться в директории `tmp/deploy/images/qemux86-64/` внутри вашей сборки. Основной файл для образа будет называться `core-image-minimal-qemux86-64.spdx.tar.zst`. Внутри этого архива будет несколько JSON-файлов, включая индексный SBOM для всего образа и SBOM для отдельных рецептов (например, для `curl`).

## Встроенный механизм `cve-check`
Yocto имеет собственный класс для проверки CVE, который не требует внешних сканеров.

Добавим в конфиги следующее:
```bash
INHERIT += "cve-check"
```
Можно запустить проверку для конкретного пакета, например, для `curl`:
```bash
bitbake -c cve_check curl
```
или всего образа привычной командой
```bash
bitbake core-image-minimal
```
Отчет в формате JSON будет создан по пути `tmp/log/cve/cve-summary.json`. В нем будет указано, какие CVE найдены, их статус (Patched/Unpatched) и другая информация.

Важно: `cve-check` использует сопоставление по CPE (Common Platform Enumeration). Это может приводить к ложным срабатываниям (False Positives), если CPE-имя рецепта совпадает с уязвимым продуктом, но уязвимый код в силу флагов сборки (как в вашем случае с `nghttp2`) в образ не попал.

Желтый текст это 
```bash

```

Предположения, почему так много `unpatched CVE` (проверить):
1. Грубый маппинг по CPE: Встроенный `cve-check` ищет уязвимости по имени продукта (CPE). Он видит, что у вас стоит `linux-yocto` версии `6.6.151`, и автоматически «примеряет» к нему все CVE, когда-либо зарегистрированные в базе NVD для ядра Linux (а их десятки тысяч).
2. В образе нет половины кода: В образ `core-image-minimal` для `qemux86-64` физически не включены драйверы для Wi-Fi карт, специфических файловых систем или экзотических сетевых протоколов. Однако сканер этого не знает и выдает предупреждение, даже если уязвимый код вообще не компилировался.
3. Backport-патчи: Разработчики Yocto часто не поднимают версию ядра целиком (до 6.6.152 и т.д.), а переносят (backport) только критические исправления безопасности в вашу текущую версию. Из-за этого формально версия кажется «старой» и уязвимой, хотя дыра уже закрыта.

### Проверка, есть ли исходный код в сборке
Будем брать какие-нибудь CVE из этого списка, находить в интернете, за какой модуль она отвечает (например, драйвер Bluetooth или подсистема памяти) и проверять, а есть ли вообще этот исходный файл в нашем образе с помощью `DWARF` и `-dbg` пакетов.

Если сканер сказал, что уязвимость есть, а в DWARF-информации этого кода нет -- значит, сканер выдал False Positive результат.

1. Файл отчета у нас лежит в `build-a/tmp/log/cve/cve-summary.json`.
2. Посмотрим на интересующий нас пакет `curl` и его зависимости. Чтобы найти строки, связанные с `curl` сначала установим `jq` -- утилиту командной строки для фильтрации JSON (с `grep` получилась нечитаемая каша, **возможно, стоит написать скрипт на питоне**):
 ```bash
jq -r '.package[] | select(.name=="curl") | .issue[] | select(.status=="Unpatched") | "\(.id) - \(.status)"' tmp/log/cve/cve-summary.json
 ```

5. Рассмотрим одну из уязвимостей в сборке A: `CVE-2026-11856` -- уязвимость в libcurl, связанная с утечкой состояния HTTP-аутентификации Digest при междоменных (cross-origin) запросах. Починили в версии libcurl `8.21.0`.
6. Посмотрим, какая версия libcurl в нашей сборке. При сборке образа автоматически создается файл `.manifest`, который содержит список всех установленных пакетов с их архитектурой и версией. В моем случае он выглядит так:
```bash
tmp/deploy/images/qemux86-64/core-image-minimal-qemux86-64.rootfs.manifest
```
Посмотрим, какая версия libcurl у нас используется:

```bash
anya@DESKTOP-RU7GHPB:~/yocto/poky/build-a/tmp/deploy/images/qemux86-64$ grep -iE "curl|nghttp2" core-image-minimal-qemux86-64.rootfs.manifest
curl core2_64 8.7.1
libcurl4 core2_64 8.7.1
```
Очевидно, что версия старше исправленной, поэтому с точки зрения сканнера уязвимость найдена правильно.
